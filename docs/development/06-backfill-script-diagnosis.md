## 2. 确定根因

### 2.1 东方汇理 `limit=200` 导致接口超时

东方汇理脚本把股份类别目录分页设为 200：

```python
PAGE_LIMIT = 200
```

同一接口实测：

| limit | HTTP | 耗时 |
|---:|---:|---:|
| 20 | 200 | 1.58s |
| 50 | 200 | 1.99s |
| 100 | 200 | 2.50s |
| 200 | 超时 | 35s 无响应 |

目录加载在逐行补全之前，因此一次 `limit=200` 超时会中止整张东方汇理表，并把尚未输出的 5 行标成“补全脚本退出码 2”。

修复为 `PAGE_LIMIT=100`。修复后同一任务工作簿的 5 行均正常返回：

```text
官网暂未发布月报，跳过
```

### 2.2 博时 DNS 瞬时失败放大为整表失败

首次任务中：

```text
ConnectionError: Failed to resolve 'www.bosera.com.hk'
```

目录加载失败，导致博时 9 行全部退出码 2。官网恢复后重新执行，9 行全部正常返回 SKIP：

- 官网未收录；
- 官网暂未发布月报；
- 官网显示清算中。

因此这 9 行不是代码匹配失败，也不应继续显示为“脚本失败”。

### 2.3 易方达 502 是下载阶段错误

BIE718 的补全结果已成功写入，随后季度报告 CDN 返回 502。独立下载重试后成功；这类错误属于下载站点瞬时故障，不应混同为补全失败。

## 3. GUI 与 Web 补全编排差异

公司补全脚本本身只有一份，GUI 和 Web 调用的是相同文件。差异在编排层：

| 行为 | 原 GUI | 修复前 Web | 影响 |
|---|---|---|---|
| 补全结果写回工作簿 | 每收到一个 `OK` 立即写 I/J | 等脚本结束后只写数据库 | 多脚本页表无法复用前一个脚本结果 |
| 同页多脚本处理范围 | 后一个脚本重新扫描，只处理仍缺行 | 每次把全部目标行传给所有脚本 | 重复认领、重复请求和多余 SKIP |
| 未认领结果 | HK/TW 均未匹配时给出明确原因 | 统一为“补全脚本未返回该行结果” | 故障不可判断 |
| 目录网络异常 | 无统一重试 | 同样无统一重试 | 单次超时中止整表 |
| 单行网络异常 | resolver 异常可中止整表 | 同样可中止整表 | 一行失败拖垮其余行 |
| 退出码原因 | 简略“退出码 2” | 同样是简略退出码 | 无法区分限流、超时、DNS |

此次修复后 Web 编排与 GUI 语义对齐，并补上 GUI 也缺少的网络容错。

## 4. 修复内容

1. `amundi_fund_link.py`：分页从 200 调整为 100。
2. `fund_link_backfill.py`：
   - 公司目录加载增加 3 次指数退避重试；
   - 单基金 resolver 增加 3 次网络重试；
   - 重试耗尽后逐行输出带根因的 SKIP，不再退出 2 中止整表。
3. Web `adapters.py`：
   - 每个脚本成功后立即把 I/J 写回任务隔离工作簿；
   - 同页多脚本后续只处理尚未成功补全的行；
   - 保留“脚本中途失败前已输出的有效 OK”；
   - 退出码错误追加脚本输出的实际原因；
   - 富达 HK/TW 均未认领时输出“港台两套补全脚本均未匹配到月报”。
4. `fullgoal_fund_link.py`：
   - 未匹配产品从返回 `None` 改为明确 SKIP“官网未收录或已下架”。


缺口原因分布主要来自：

不能通过把 SKIP 改成成功或伪造 I/J 达成。
